# Project Guidelines

@AGENTS.md

## Stack

- **PHP 8.4+** (Sail runs 8.5, CI tests 8.4 and 8.5) / **Laravel 13** / **Inertia v3** / **Vue 3** / **Tailwind CSS v4**
- **Database**: PostgreSQL (via Laravel Sail/Docker)
- **Package manager**: npm (not bun/pnpm)
- **Dev environment**: Laravel Sail (`sail up -d`)
- **Wayfinder**: dev-next branch (generates full TypeScript: routes, actions, models, enums, Inertia props, broadcast channels, env vars)

## Commands

All commands should be run through Sail to ensure correct platform bindings and database access.

- `sail up -d` — Start Docker containers
- `sail composer dev` — Start full dev environment (server, queue, logs, vite)
- `sail composer test` — Run full test suite (unit + lint + static analysis + 100% type coverage)
- `sail composer lint` — Auto-fix: rector + pint + eslint
- `sail npm install` — Install npm dependencies (run once after cloning, or after package.json changes)
- `sail npm run dev` — Regenerate Wayfinder types + start Vite dev server
- `sail npm run build` — Build frontend assets (required before running tests)
- `composer update:requirements` — Bump composer.json + package.json versions (run manually)

**Important**: Always use `sail npm` instead of bare `npm` — native bindings (ESLint resolvers, etc.) are platform-specific and must match the container's Linux architecture.

## Architecture

### Actions Pattern

- Business logic lives in `app/Actions` as dedicated Action classes.
- Actions have **only** a `handle()` method — no private helpers, no extra methods. If an action needs a helper, either inline the logic or extract it into a separate action or support class.
- Create with `php artisan make:action "{name}" --no-interaction`.
- Inject dependencies via constructor using private properties.
- Wrap complex operations in `DB::transaction()` when multiple models are involved.
- Actions are called from jobs, commands, HTTP requests, API requests, MCP requests, etc.
- Complex flows should be split into multiple focused actions.

```php
<?php

declare(strict_types=1);

namespace App\Actions;

final readonly class CreateFavorite
{
    public function __construct(private FavoriteService $favorites)
    {
        //
    }

    public function handle(User $user, string $favorite): bool
    {
        return $this->favorites->add($user, $favorite);
    }
}
```

### Controllers & Validation

- **Controllers must be thin.** They coordinate Actions, Form Requests, and Inertia responses — nothing else. No query building, no data transformation, no string parsing. If logic doesn't fit in one readable line, extract it into an Action or a Form Request method.
- Always create Form Request classes for validation — no inline validation in controllers. Use typed accessor methods on Form Requests (e.g., `$request->search()`) to encapsulate parsing and casting — keep controllers free of raw input handling.
- **Always use `$request->validated()` to access input in controllers** — never use `$request->input()`, `$request->get()`, `$request->string()`, `$request->integer()`, `$request->boolean()`, or `$request->query()` after validation. These bypass the validation layer and can allow unvalidated data through. The only safe accessors are `$request->validated()`, `$request->validated('key')`, and typed methods defined on the Form Request itself.
- Use Form Request `after()` methods for business-rule validation that goes beyond field formatting (e.g., checking an active connection exists before allowing a reply). This keeps authorization-like checks in the validation layer rather than scattering them across controllers or actions.
- Use `Inertia::render()` for server-side routing, not Blade views.
- Use `php artisan make:` commands for new files. Pass `--no-interaction` to all artisan commands.

### Models & Database

- Use Eloquent relationships with return type hints. Prefer `Model::query()` over `DB::`.
- Prevent N+1 queries — use eager loading (`$with` or `::with()`).
- When creating models, also create factories and seeders.
- Casts go in a `casts()` method, not the `$casts` property.
- **All models use ULIDs, never auto-increment IDs.** Add the `HasUlids` trait to the model and use `$table->ulid('id')->primary()` and `$table->foreignUlid('...')` in migrations (`make:model` still generates `$table->id()` — change it). Polymorphic columns already default to ULIDs (`Builder::morphUsingUlids()`). An architecture test enforces the trait.

### Bot Protection

- Public forms that send emails or create records (registration, password reset, contact forms) must be rate limited and protected by the honeypot.
- Backend: add a named `throttle:` limiter and the `ProtectAgainstBots` middleware to the route. Frontend: place `<BotProtection />` inside the `<Form>`. The honeypot fields are shared with every page as the `botProtection` Inertia prop.
- Fortify's register and forgot-password POST routes are redefined in `routes/auth.php` to add this protection; keep them in sync if Fortify paths change.
- In tests, submit `...$this->botProtectionFields()` with the payload.

### Error Handling

- Use **renderable exceptions** (Laravel 13 pattern) for domain-specific errors. Define a `render(Request)` method on the exception class that returns the appropriate response for JSON or Inertia requests.
- Controllers stay clean — no try/catch. Exceptions bubble up and render themselves.
- Frontend Inertia pages access errors via `usePage().props.errors`.

## PHP Style

- `declare(strict_types=1)` in all PHP files.
- `final` classes by default. `final readonly` for Actions and value objects.
- Strict comparisons (`===`), no loose checks.
- Use PHP 8 constructor property promotion.
- Always use explicit return type declarations and type hints.
- Always use curly braces for control structures, even single-line.
- No superfluous annotations — only `@` annotations for typing variables.
- PHPDoc blocks over inline comments. No comments within code unless genuinely complex.
- Enum keys in TitleCase (e.g., `FavoritePerson`, `Monthly`).
- Use descriptive names: `isRegisteredForDiscounts`, not `discount()`.

## Frontend Style

- TypeScript everywhere — no `any` types.
- Import Wayfinder from `@/wayfinder/` paths (not `@/routes/` or `@/actions/`).
- Prefer named imports for tree-shaking: `import { show } from '@/wayfinder/App/Http/Controllers/PostController'`.
- Use the `<Form>` component from Inertia v3 with Wayfinder: `<Form v-bind="store.form()" ...>`. Prefer `Form` component over `useForm` hook.
- ESLint + Prettier + vue-tsc for linting/formatting/type checking.

### Types — Always Use Wayfinder

- **Never define local interfaces for models or enums.** Import from `@/wayfinder/types` instead:
  ```typescript
  import type { App } from '@/wayfinder/types';
  // Use: App.Models.Message, App.Models.Conversation, App.Enums.Provider, etc.
  ```
- For subsets of a model (e.g., a component that only needs some fields), use `Pick<>`:
  ```typescript
  type SummaryUser = Pick<App.Models.User, 'id' | 'name' | 'email'>;
  ```
- For extended types (e.g., a model with an appended attribute or eager-loaded relation), use intersection:
  ```typescript
  type PostWithAuthor = App.Models.Post & {
      author: Pick<App.Models.User, 'name'>;
  };
  ```

### Shared Code

- **Composables** live in `resources/js/composables/` — reusable reactive logic.
- **Utility functions** live in `resources/js/utils/` — pure functions with no Vue reactivity.
- If the same logic appears in 2+ components, extract it. Don't copy-paste computed properties or formatting functions.

### Inertia Patterns

- Use `async: true` on `router.post`/`router.get` for background requests that shouldn't show the browser loading indicator.
- Use `preserveState: true` + `preserveScroll: true` to avoid visible page reloads on navigation within the same page.
- Use `optimistic` option on router visits for instant UI updates that auto-revert on failure:
  ```typescript
  router.get(url, data, {
      optimistic: (props) => ({ items: props.items.map(...) }),
  });
  ```

### Dark Mode

- **Always use semantic Tailwind classes** (`text-foreground`, `text-muted-foreground`, `bg-muted`, `text-destructive`, `bg-accent`, etc.) instead of hardcoded colors (`text-gray-600`, `text-neutral-600`, `text-red-500`). Semantic classes adapt to both light and dark themes automatically.
- When semantic classes don't provide enough contrast in dark mode, use `dark:` variants with transparent white overlays (e.g., `dark:bg-white/[0.08]`, `dark:ring-1 dark:ring-white/[0.06]`).
- For status colors that must be hardcoded (green for connected, amber for warnings), always include a `dark:` variant (e.g., `text-green-600 dark:text-green-400`).
- Test every UI change in both light and dark mode before finalizing.

### Accessibility

- Decorative SVG icons (used alongside text labels) must have `aria-hidden="true"`.
- Interactive icon-only buttons must have an accessible label (via `aria-label` or a visually hidden `<span>`).

### Frontend File Organization

Pages are organized as **directory-per-feature** under `resources/js/pages/`:

```
pages/
  dashboard/
    Index.vue                <- main page for the feature
    Show.vue                 <- sub-pages if needed
    components/              <- components only used by this feature
      StatCard.vue
  settings/
    Profile.vue
    Security.vue
    Appearance.vue
```

**Rules:**
- Each feature gets its own directory under `pages/` with an `Index.vue` as the entry page.
- Feature-specific components go in `pages/<feature>/components/` and are imported via relative paths (`./components/ProviderCard.vue`). Per ESLint config, relative imports come before `@/` aliased imports.
- Shared/reusable components live in `resources/js/components/` and are imported via `@/components/`.
- If a component is only used within one feature, colocate it. If used across features, promote it to `components/`.

## Wayfinder (dev-next)

- All generated types live under `resources/js/wayfinder/` (gitignored).
- Routes: `import { dashboard } from '@/wayfinder/routes'`
- Actions: `import { show } from '@/wayfinder/App/Http/Controllers/PostController'`
- Named routes: `import { edit } from '@/wayfinder/routes/profile'`
- Form variants: `<Form v-bind="store.form()">`

- Run `php artisan wayfinder:generate` after route/controller changes if Vite isn't running.

## Code Quality Tools

- **Pint**: Code formatter with strict rules (strict_types, final_class, strict_comparison, ordered class elements). Config in `pint.json`.
- **Rector**: Automated refactoring (dead code, type declarations, early returns, code quality). Config in `rector.php`.
- **Larastan/PHPStan**: Static analysis at level 6. Config in `phpstan.neon`.
- **Pest architecture tests** (`tests/Unit/ArchitectureTest.php`): enforce the rules in this file — Actions are `final readonly` with only `handle()`, controllers don't use `DB`, no `env()` outside config, no debug functions, models use ULIDs, plus Pest's `php`, `security` and `laravel` presets. When a rule changes here, update the test too.
- **Type coverage**: `pest --type-coverage --min=100`.
- **ESLint**: Vue/JS/TS linting with import ordering.
- **Prettier**: Code formatting with Tailwind CSS plugin.
- **vue-tsc**: TypeScript type checking for Vue.

## Testing

- Tests use **Pest** (not PHPUnit). Run through Sail: `sail composer test`.
- Tests require PostgreSQL (Docker via Sail) and built Vite assets (`npm run build`).
- Every change must be tested. Write or update a test, then run it.
- Create tests with `php artisan make:test --pest {name}` (feature) or `php artisan make:test --pest --unit {name}` (unit).
- Use factories for model creation in tests.
- Run minimal tests with filter: `sail artisan test --compact --filter=testName`.
- Feature tests in `tests/Feature/`, unit tests in `tests/Unit/`.
- Use Pest syntax: `test('name', fn () => ...)` or `it('does something', function () { ... })`.
- Use `expect()` API for assertions where appropriate.
- Use datasets for tests with duplicated data (e.g., validation rules).

## Environment & Config

- Never use `env()` outside config files. Use `config('app.name')`.
- Use environment variables only in configuration files.
- `.env` is gitignored. `.env.example` is committed.

## Before Finalizing Changes

1. Run `composer lint` to auto-fix PHP and JS issues.
2. Run `npm run build` to rebuild frontend assets.
3. Run `sail composer test` to verify everything passes.

## Do Not

- Do not change dependencies without approval.
- Do not create new base folders without approval.
- Do not remove tests without approval.
- Do not create documentation files unless explicitly requested.
- Do not use raw DB queries — use Eloquent.
- Do not use inline validation — use Form Requests.
- Do not access request input via `$request->input()`, `$request->string()`, `$request->integer()`, `$request->boolean()`, `$request->enum()`, or `$request->query()` in controllers — always use `$request->validated()` or typed Form Request accessor methods.
- Do not use hardcoded color classes (`text-gray-600`, `text-red-500`, `bg-neutral-100`) for text, backgrounds, or borders — use semantic Tailwind classes (`text-foreground`, `text-destructive`, `bg-muted`).
